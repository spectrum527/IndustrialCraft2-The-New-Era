# 版本协商与 echo（P2-T6）

## §1 协商与连接范围

两个目标版本均登记必需的 IC2 play payload。网络协议版本是固定字符串 `1`，与模组发行号独立。客户端和服务器连接时由 NeoForge 的版本化 payload registrar 协商种类、方向及协议版本。双方均支持这份声明才可进入可用的玩法连接。缺少必需声明或协议版本不一致，连接须被拒绝，echo 处理次数为零。每次重新连接都重新协商。协议只约定相同 Minecraft 目标版本内的连接。[NeoForge 1.21.1 payload 注册](https://docs.neoforged.net/docs/1.21.1/networking/payload/)

## §2 消息与单位

| 注册 ID | 逻辑方向 | 消息体 | 接收后的结果 |
| --- | --- | --- | --- |
| `ic2:echo_request` | 客户端 → 服务器 | 8 字节有符号整数，二进制补码，大端序 | 仅向发出此请求的实际连接发送一次相同序号的回执。 |
| `ic2:echo_reply` | 服务器 → 客户端 | 同上 | 该客户端可以读取回执序号，关联其请求。回执不触发新的请求。 |

消息体不含字符串或内部长度前缀。8 字节上限仅计 IC2 消息体。宿主另行编码通道 ID 及传输帧头。合法值覆盖整个 64 位有符号范围，包括零、负数和两个端点。请求不接受客户端自报的发送者或目标，echo 不改变玩家、库存或世界。

## §3 发送、接收和线程

登记在版本模块完成。共同层给出消息声明和显式编解码。客户端发送至当前服务器，服务端用收到请求的连接回复。接收侧先以宿主连接确认方向和阶段，再验证确切长度和完整消费。只有合法帧能交给相应逻辑侧宿主线程上的业务处理器。1.21.1 与 26.1 的客户端处理器均须隔离物理客户端类型。专服可以登记两条消息并发送回执。[共同边界 §4](services.md)

## §4 失败与清理

本地对未登记消息、错误方向、断开连接或无效编码的发送显式失败。传输中，归属 IC2 的未知 play ID、错向、少于或多于八字节的消息均不得进入 IC2 处理器、产生回执或更新客户端结果。宿主在分派前拒绝或断开违规连接即可。若宿主将未知通道交给其他机制，IC2 仍不得将其当作 echo。断开时清理该连接的待收请求或最后回执，再连时不能看到上次会话的结果。B#31 的旧式 GUI 显示子包已移除。

## §5 通过条件

组件测试核对边界数、正负数和逐字节往返。例如序号 `0x0102030405060708` 的八字节依次为 01、02、03、04、05、06、07、08。分别输入 0、7、9 字节体、未知 ID、相反方向和断开连接，记录拒绝及业务处理次数。注册冲突不得覆盖原处理器。验证两个 peer 时各自收回自己的序号。

在 1.21.1 独立客户端和专服实际连接后，客户端发起一个可识别的序号。两端日志须能对应协商、服务端接收、服务端向该连接回复、客户端收到相同值，服务器只处理一次。用改变协议版本的独立开发客户端再次连接，记录玩法阶段前的拒绝及零次 echo。开发驱动及不兼容变体留在测试环境。双版本分别编译实际登记桥接。26.1 的运行门禁自 P6 起。[构建取证](verification.md)

## §6 26.x 专服原生配方同步

在 NeoForge 26.1.2 与 26.2 分别用同目标的独立客户端和专服，加载含 IC2 设备挂接配方的世界。首次连接须完成原生配方同步 `neoforge:recipe_content`、进入玩法并用合成格完成一项设备挂接配方。服务端执行 `/reload` 后，当前连接仍能使用该配方。离开并重新进服后，再用该配方验证正确的输入消耗和产物。三次均核对服务器与客户端结果及连接状态。
